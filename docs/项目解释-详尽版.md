# KG_Scene_Retrieval 项目解释（详尽版）

## 1. 先统一当前项目的真实边界

在理解任何细节前，先把当前系统的真实边界说清楚：

- 当前最终检索模态只有 `text2image` 和 `text2video`
- Milvus 存的是帧级实体，不是视频级实体
- `text2video` 不是直接检索视频，而是先检索命中帧，再围绕命中帧收集同一 scene、同一 camera 的连续帧生成视频
- Neo4j 存的是 scene 级结构化知识，不存图像向量
- Gradio 页面只是最终展示入口，不是检索逻辑本体

这 5 句话是理解整个仓库的总前提。

还要再补一句当前运行口径：

- 旧说明中经常以 `nuScenes v1.0-mini` 讲解概念
- 当前代码实际运行配置以 [config.py](/D:/KG_Scene_Retrieval/config.py) 为准
- 当前默认配置已经切到 `v1.0-trainval` 的相机子集 `trainval_camera_part06_part10`

因此，你在读代码时要把“概念讲解口径”和“当前运行配置”区分开：

- 概念讲解：仍可借助 `nuScenes` 通用 schema 理解
- 真正运行：以 `config.py`、`derived_data/`、`csvdata/`、当前 Milvus collection 和 benchmark 为准

## 2. 这个项目到底在做什么

这是一个面向自动驾驶场景的跨模态检索系统。

用户输入一句中文或英文场景描述后，系统会完成以下工作：

1. 从自然语言中提取天气、时段、地点、对象等结构化条件
2. 在 scene 级知识图谱中筛出候选场景
3. 选择合适的 CLIP 文本编码模型
4. 在 Milvus 中检索最相似的图像帧
5. 将结果展示为图片，或围绕命中帧生成视频片段

可以把它压缩成一句话：

```text
先做 scene-level filtering，再做 frame-level retrieval，最后做 result rendering。
```

## 5. 系统分层理解

### 第 1 层：原始数据层

这一层是 nuScenes 的原始 metadata 和图像文件。

典型依赖包括：

- `scene.json`
- `sample.json`
- `sample_data.json`
- `sample_annotation.json`
- `instance.json`
- `category.json`
- `log.json`
- `samples/`
- `sweeps/`

核心关系是：

```text
scene -> sample -> sample_data -> image
sample -> sample_annotation -> instance -> category
```

### 第 2 层：scene 结构化层

这一层由 [src/kg_builder.py](/D:/KG_Scene_Retrieval/src/kg_builder.py) 主导。

它把原始 metadata 整理成 scene 级 record，每条 record 通常包含：

- `scene_token`
- `scene_name`
- `description`
- `weather`
- `timeofday`
- `location_area`
- `location_kind`
- `objects`

### 第 3 层：知识图谱层

Neo4j 中的核心节点和关系大致是：

- `Scene`
- `Weather`
- `TimeOfDay`
- `Location`
- `Object`

关系包括：

- `Scene -[:WEATHER]-> Weather`
- `Scene -[:TIMEOFDAY]-> TimeOfDay`
- `Scene -[:LOCTYPE]-> Location`
- `Scene -[:CONTAINS]-> Object`

它的作用是：

```text
根据结构化条件先筛 scene，而不是做向量相似度排序。
```

### 第 4 层：自然语言理解层

这一层由 [src/nlp_parser.py](/D:/KG_Scene_Retrieval/src/nlp_parser.py) 提供。

例如查询：

```text
rainy night intersection with pedestrians
```

可能被解析为：

- `weather = rainy`
- `time = night`
- `location = intersection`
- `objects = ["pedestrian"]`

解析结果会直接影响：

- KG 过滤条件
- 模型选择
- 前端解释面板展示

### 第 5 层：帧级向量检索层

这一层由 [scripts/insert_image.py](/D:/KG_Scene_Retrieval/scripts/insert_image.py) 和 [src/milvus_utils.py](/D:/KG_Scene_Retrieval/src/milvus_utils.py) 支撑。

重要事实：

- 写入的是图像帧向量，不是视频向量
- 写入时会同时补充业务元数据
- 检索返回的是相似帧命中列表

### 第 6 层：检索编排层

这一层由 [app.py](/D:/KG_Scene_Retrieval/app.py) 负责。

主流程可以概括为：

```text
query
-> parse_query
-> query_scene_tokens / local KG fallback
-> encode_text_query
-> search_frame_hits
-> enrich_hit_record
-> progressive fallback if needed
-> return image results or derive video results
```

这里还包含工程化回退逻辑，例如：

- Neo4j 不可用时退到本地 KG
- 严格 scene 过滤没有命中帧时，按规则放宽位置条件
- 必要时回退到更宽的相似度搜索范围

### 第 7 层：结果生成与展示层

最终结果有两种：

#### `text2image`

- 直接展示命中的图像帧
- 附带分数和解释性元数据

#### `text2video`

- 先检索到锚点帧
- 再到同一 scene、同一 camera 的时序中收集连续帧
- 动态渲染为视频文件并在 UI 中展示

所以必须明确区分：

- Milvus 中存的是帧级实体
- 视频是应用层派生输出

## 6. 评估与论文实验

[scripts/evaluate.py](/D:/KG_Scene_Retrieval/scripts/evaluate.py) 说明这个仓库不仅是 UI demo，也是 benchmark 平台。

当前常见策略包括：

- `pure_clip`
- `kg_clip_strict`
- `kg_clip_engineering`

这三个策略不能混为一谈：

- `pure_clip`：不做 KG 过滤，直接全库帧检索
- `kg_clip_strict`：更适合论文主实验，强调严格 KG 条件
- `kg_clip_engineering`：更接近当前产品化 / 界面行为，强调回退与稳定返回

仓库中的 [benchmark/](/D:/KG_Scene_Retrieval/benchmark) 和 [benchmark/runs/](/D:/KG_Scene_Retrieval/benchmark/runs) 保存了评估输入、结果和报告资产。

## 附录 A：`config.py` 逐组解释

前面的正文已经说了 `config.py` 很重要，但如果你第一次打开这个文件，仍然会觉得它像一大串路径和常量。这里把它拆开讲。

### A.1 项目根与资源回退

当前配置里最先定义的是：

- `PROJECT_ROOT`
- `ORIGINAL_PROJECT_ROOT`

这两个量的意义不是重复，而是服务于“当前工作目录”和“原始项目目录”并存的场景。

接着定义了：

- `resolve_resource_dir(local_dir, fallback_dir)`

它的作用是：

- 优先用当前工作区里的资源目录
- 如果当前目录里没有，就回退到原始项目目录里的同名资源

这类设计常见于：

- 多 worktree
- 本地复制项目目录
- 模型或静态资源不想重复放多份

### A.2 模型与 CSV 配置

这一组包括：

- `MODELS_DIR`
- `ENGCLIP_MODEL_DIR`
- `CHNCLIP_MODEL_DIR`
- `CHNCLIP_REPO_ID`
- `CSV_DIR`
- `IMAGE_CSV_PATH`
- `TEXT_CSV_PATH`

它们分别决定：

- English-CLIP 从哪里加载
- Chinese-CLIP 从哪里加载
- 图像入库时从哪个 CSV 读取 `id/path`
- 某些文本资源从哪里读取

这里最关键的是：

- 当前在线检索并不直接扫描整个数据集目录找图片
- 它很多地方先依赖 `IMAGE_CSV_PATH` 完成 `id -> path` 的对齐

所以 CSV 不是小配角，而是当前系统的路径索引入口之一。

### A.3 trainval 子集与 metadata 配置

这一组包括：

- `TRAINVAL_SUBSET_NAME`
- `TRAINVAL_ASSET_DIR`
- `TRAINVAL_ROOT`
- `NUSCENES_VERSION`
- `NUSCENES_META_ROOT`
- `NUSCENES_META_SOURCE_DIR`
- `NUSCENES_META_DIR`
- `NUSCENES_SCENE_TOKEN_PATH`
- `NUSCENES_SUBSET_REPORT_PATH`
- `NUSCENES_BLOB_ROOTS`
- `NUSCENES_PRIMARY_BLOB_ROOT`
- `NUSCENES_ROOT`
- `NUSCENES_SAMPLES_DIR`
- `NUSCENES_SWEEPS_DIR`
- `NUSCENES_MAPS_DIR`
- `PRIMARY_CAMERA`

这组配置决定的是：

- 当前实验到底在用哪个 trainval 子集
- metadata 读取的是筛选后的子集目录，还是原始 metadata
- 在线应用主要去哪些 blob root 解析真实图像文件
- 默认主相机是谁

其中最容易混淆的点是：

- `NUSCENES_META_SOURCE_DIR`
  - 更接近原始 metadata 来源
- `NUSCENES_META_DIR`
  - 更接近当前项目真正运行时读取的“子集 metadata”

### A.4 服务与数据库配置

这一组包括：

- `APP_PORT`
- `ATTU_PORT`
- `MILVUS_HOST`
- `MILVUS_PORT`
- `NEO4J_URI`
- `NEO4J_USER`
- `NEO4J_PASSWORD`
- `NEO4J_HTTP_PORT`

它们分别影响：

- Web UI 的访问端口
- Attu 的访问端口
- Milvus 连接
- Neo4j 连接

注意：

- `start.bat` 会从 `config.py` 动态读取这些值
- 也就是说，批处理脚本没有偷偷维护另一套端口常量

### A.5 Milvus collection 配置

这一组包括：

- `MILVUS_COLLECTION_NAME`
- `MILVUS_VECTOR_DIM`
- `MILVUS_INDEX_TYPE`
- `MILVUS_METRIC_TYPE`
- `MILVUS_NLIST`
- `MILVUS_NPROBE`
- `DEFAULT_TOP_K`
- `IMAGE_ID_MIN`

这里的重点有两个。

第一，collection 名会决定：

- 入库脚本把数据写到哪里
- 在线检索从哪里读

第二，`IMAGE_ID_MIN` 说明当前检索代码可能会显式忽略一部分较小 id 的记录，这通常意味着：

- 当前 collection 历史上可能混入过旧记录
- 或者当前项目把某个 id 段当作“有效图像区间”

### A.6 视频生成配置

这一组包括：

- `GENERATED_VIDEO_DIR`
- `VIDEO_FPS`
- `VIDEO_MAX_FRAMES`
- `VIDEO_FRAME_STRIDE`
- `VIDEO_RESULT_COUNT`
- `VIDEO_SEARCH_LIMIT`
- `VIDEO_TRANSITION_FRAMES`
- `VIDEO_OUTPUT_MAX_WIDTH`
- `HIT_METADATA_CACHE_SIZE`
- `VIDEO_CLIP_CACHE_SIZE`
- `ENABLE_RETRIEVAL_TIMINGS`

它们会影响：

- 视频片段采样密度
- 一次返回多少个视频候选
- 视频输出尺寸
- 是否启用耗时统计
- 运行时缓存规模

如果未来你要调“视频看起来更长、更流畅、更轻量”，大概率改的就是这里。

## 附录 B：原始 nuScenes 表在这个项目里是怎么被用起来的

前面正文已经解释了各表的角色，这里进一步用“代码里的映射关系”再串一次。

### B.1 `scene.json` 到 `sample.json`

关键关系：

- 一个 `scene` 拥有多个 `sample`

代码里最常见的映射方式是：

- `sample_to_scene = {sample_token: scene_token}`

这一步非常关键，因为后面：

- `sample_annotation`
- `sample_data`

都需要通过 `sample_token` 才能回到所属 scene。

### B.2 `sample.json` 到 `sample_data.json`

关键关系：

- 一个 `sample` 下面会挂多个 `sample_data`
- 不同 `sample_data` 分别对应不同传感器通道

当前项目关心的主要是图像型 `sample_data`，也就是：

- `.jpg`
- `.jpeg`
- `.png`

### B.3 `sample_annotation.json` 到 `instance.json`

关键关系：

- 一个 annotation 记录某个 sample 里出现的一个对象实例
- 它会带 `instance_token`

于是当前项目会先走：

```text
annotation -> instance
```

再走：

```text
instance -> category
```

最终拿到：

```text
这个 sample / scene 出现了什么对象类别
```

### B.4 `category.json` 的作用为什么不只是“显示名称”

如果没有 `category.json`，项目只能知道：

- 某个 instance 存在

但不会知道：

- 它到底是行人、汽车、公交车还是锥桶

也就是说，这张表决定了 KG 和 NLP 最终能不能在“对象语义”上对齐。

### B.5 `log.json` 为什么会影响检索

很多人第一次看会以为 `log.json` 只是背景信息。

但在这个项目里，`log.location` 会被转成：

- `location_area`
- `location_key`

这意味着它不仅影响展示，还会影响：

- scene 结构化描述
- KG 中的位置节点
- 某些 scene 间辅助关系

## 附录 C：`src/kg_builder.py` 的函数级说明

这一附录专门从“函数级职责”再读一遍 KG 构建模块。

### C.1 `read_json_records`

作用：

- 读取一个 JSON 文件并返回记录列表

它本身很简单，但它是很多更高层函数的基础。

### C.2 `normalize_object_name`

作用：

- 把 nuScenes 原始类别统一成项目内部对象名

为什么这一步必须有：

- 原始类别层级太细
- 用户查询一般不会说 `human.pedestrian.adult`
- KG 节点也不适合挂太细的原始类别名

### C.3 `infer_weather`

作用：

- 从 scene 描述中推断天气

它不是视觉检测，而是基于 description 的关键词启发式。

所以你要知道：

- 它表达的是“scene 文本描述中的天气语义”
- 不是像素级天气真值

### C.4 `infer_time_of_day`

作用：

- 从描述中推断时段

目前是：

- `night`
- `dusk`
- `day`

### C.5 `infer_location_kind`

作用：

- 从描述中推断场景地点类型

例如：

- 路口
- 人行横道
- 停车场
- 公交站
- 人行道
- 高速
- 街道

### C.6 `load_metadata_tables`

作用：

- 批量把构建 scene records 所需的表一次性读入

它是“scene 结构化整理”的数据装载入口。

### C.7 `build_scene_records`

这是当前模块最核心的函数。

它值得再按步骤详细解释一遍：

1. 读入 `scene`、`log`、`sample`、`sample_annotation`、`instance`、`category`
2. 建 `sample -> scene`
3. 建 `instance -> category`
4. 遍历 annotation，把对象实例聚合到所属 scene
5. 统计对象计数
6. 从 scene 描述中推断天气、时段、地点
7. 产出 scene 级 record

这一过程本质上是在做：

```text
把细粒度标注事实压缩成 scene 级知识摘要
```

### C.8 `filter_scene_records`

作用：

- 在 Python 内存里做 scene 条件过滤

它当前是 Neo4j 的本地替代方案。

这意味着即使：

- Neo4j 没启动
- Neo4j 查询失败

系统仍然可以用 `KG_SCENE_RECORDS` 做一定程度的 scene 过滤。

### C.9 `get_neo4j_driver`

作用：

- 统一构造 Neo4j driver

### C.10 `create_constraints`

作用：

- 确保关键节点上的唯一性约束存在

这样可以避免：

- 重复 scene 节点
- 重复 weather 节点
- 重复 object 节点

### C.11 `write_scene_graph`

作用：

- 把 scene records 写成 Neo4j 图

它做的不是批量导表，而是显式地创建：

- 节点
- 关系
- 辅助邻接关系

### C.12 `query_scene_tokens`

作用：

- 根据结构化条件返回匹配的 `scene_token`

你可以把它看作：

```text
在线 KG scene filtering 的直接后端接口
```

## 附录 D：`src/nlp_parser.py` 的函数级说明

这一附录再从函数级把查询解析模块讲透。

### D.1 `detect_language`

这是最轻量但很关键的一步。

它通过检测中文字符决定：

- 这条查询被视为中文还是英文

这会进一步影响：

- 模型选择
- 一些关键词匹配行为

### D.2 `select_model_key`

作用：

- 根据语言返回 `chnclip` 或 `engclip`

### D.3 `_contains_keyword`

作用：

- 判断文本中是否出现某个关键词

这个函数不是简单 `in` 判断，因为：

- 英文需要考虑词边界
- 中文不需要空格分词

### D.4 `_find_keyword_matches`

作用：

- 找出关键词在原文本中的命中区间

这是后面高亮系统的基础。

### D.5 `_match_first`

作用：

- 适合那些应该只取一个值的字段

例如：

- 天气
- 时段
- 地点

### D.6 `_match_all`

作用：

- 适合对象类别提取

因为用户一句话里可以同时提到多个对象：

- 行人
- 车
- 自行车

### D.7 `_resolve_highlight_overlaps`

作用：

- 当多个关键词区间重叠时，决定最后保留哪个高亮片段

这说明解析模块不只是“提条件”，还兼顾了：

- 前端展示质量

### D.8 `parse_query`

它是整个 NLP 模块对外暴露的主入口。

你要记住它给下游提供的是一份多用途结构：

- 给 KG：`weather/time/location/objects`
- 给 CLIP：`model_key`
- 给 UI：`highlight_matches`
- 给日志和调试：`raw_text`

## 附录 E：`src/nuscenes_metadata.py` 的函数级说明

### E.2 `load_nuscenes_metadata`

### E.4 `get_blob_roots`

作用：

这对多 blob 目录结构特别重要。

### E.5 `resolve_frame_path`

作用：

- 根据各种可能的原始路径形式，找到真实图像文件

它会尝试：

- 直接路径
- 当前工作目录相对路径

### E.7 `collect_sample_object_types`

### E.8 `build_scene_metadata`

这就是为什么 `insert_image.py` 和 `app.py` 都依赖它。

## 附录 F：`app.py` 里几个最关键函数的行为说明

前面正文已经讲了主链路，这里再按函数把在线应用里最重要的几个点单独拎出来。

### F.1 `get_candidate_scene_tokens`

这是在线应用里最关键的路由函数之一。

它不只是“查一下 Neo4j”，而是在决定：

- 用不用 KG
- 用 Neo4j 还是本地 KG
- 遇到 0 候选时要不要继续往后走

理解这个函数时必须区分：

- 学术上的严格零候选停止
- 工程上的尽量稳定返回

### F.2 `encode_text_query`

这是文本编码主入口。

它负责：

- 选模型
- 组织 processor 输入
- 做截断保护
- 取文本特征
- 归一化向量

### F.3 `search_frame_hits`

这是 Milvus 搜索主入口。

它的几个特点是：

- 会优先尝试基于 `scene_token` 的 collection 侧过滤
- 会在必要时扩大搜索范围
- 会在应用层做二次筛选
- 会在 collection 状态异常时尝试刷新 collection 再重试

也就是说，它不是一个“简单的 Milvus search 包装器”，而是带了工程补偿逻辑。

### F.4 `search_hits_with_progressive_fallback`

这是当前工程回退策略的集中体现。

它处理的问题是：

- 严格候选 scene 中没有帧命中怎么办

当前优先回退策略之一是：

- 如果带地点条件，先尝试放宽地点

这说明当前系统并不是简单“要么严格命中，要么全库放弃”，而是有中间层回退。

### F.5 `retrieve_images`

这是图片结果的总入口。

它除了做主链路外，还做了：

- 各阶段耗时统计
- 图片解码
- 结果说明拼接

### F.6 `collect_video_frames`

这是视频派生结果的关键。

它保证了：

- 只在单个 scene 内取帧
- 只在单个 camera 内取帧

这也正是项目规则要求的：

- 一个视频结果不能跨多个 scene

### F.7 `write_video_clip`

这个函数的重点不只是“写视频”，而是：

- 尝试多种 codec
- 检查浏览器可播放性
- 必要时做格式转换
- 利用缓存避免重复生成

这让 `text2video` 结果更接近“可在网页中稳定播放”，而不是“理论上渲染出一个文件就算完成”。

## 附录 G：评估脚本 `scripts/evaluate.py` 的阅读重点

### G.1 为什么这个脚本值得单独细读

因为它清晰地区分了：

- 学术评估口径
- 工程运行口径

这在很多项目里是混在一起的，而这里是显式分开的。

### G.2 `strict_candidate_scene_tokens`

这是评估侧的严格 KG 候选获取逻辑。

它和在线应用的最大差别在于：

- 如果严格 KG 最终没有候选 scene，它可以真的停止

这更符合论文实验里“结构化约束是否有效”的研究目标。

### G.3 `run_pure_clip`

作用：

- 直接跑无 KG 基线

### G.4 `run_kg_clip_strict`

作用：

- 跑严格学术口径下的 KG + CLIP

### G.5 `run_kg_clip_engineering`

作用：

- 跑更接近当前线上工程逻辑的策略

### G.6 为什么要同时保留两套 KG+CLIP 逻辑

因为这两个问题不是同一个问题：

- 学术上想问：结构化约束是否真的提升了目标指标
- 工程上想问：用户查询时系统是否能稳定返回合理结果
