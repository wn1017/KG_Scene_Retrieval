# KG_Scene_Retrieval 项目解释（详尽版）

## 1. 先统一当前项目口径

在理解任何细节之前，先把当前系统的真实边界讲清楚。

- 当前最终只有两种检索模态：`text2image` 和 `text2video`
- Milvus 里存的是帧级实体，不是视频级实体
- `text2video` 不是直接检索视频，而是先检索命中帧，再围绕命中帧收集邻近帧并动态生成视频
- Neo4j 存的是 scene 级结构化知识，不存图像向量
- Gradio 页面只是最终展示入口，不是核心检索逻辑本身

这 5 句话是理解整个项目的总前提。后面所有模块，都是围绕这个事实展开的。

整个系统的主线可以压缩成一句话：

```text
先把 nuScenes 原始数据整理成 scene 级知识，
再用知识图谱筛 scene，
再用 CLIP + Milvus 检索最像的帧，
最后返回图片或围绕命中帧生成视频片段。
```

---

## 2. 项目总览

这个项目是一个面向 `nuScenes v1.0-mini` 的自动驾驶场景检索系统。

用户输入一句中文或英文的场景描述后，系统会完成如下工作：

1. 理解这句话里提到的天气、时段、地点、对象等条件
2. 从知识图谱中筛出可能相关的 scene
3. 选择合适的 CLIP 文本编码模型
4. 去 Milvus 中检索最相似的帧
5. 把结果展示成图片卡片，或围绕命中帧生成视频片段

从技术组件看，项目主要由这几部分组成：

- 数据集：`nuScenes v1.0-mini`
- 知识图谱：Neo4j
- 向量数据库：Milvus
- 视觉语义模型：English-CLIP / Chinese-CLIP
- Web 界面：Gradio

从代码组织看，关键文件是：

- `config.py`
- `app.py`
- `src/kg_builder.py`
- `src/nlp_parser.py`
- `src/nuscenes_metadata.py`
- `src/milvus_utils.py`
- `scripts/insert_image.py`
- `scripts/evaluate.py`
- `start.bat`

## 3. 先看代码里每个关键文件负责什么

这一节不是七层分层，而是帮助你先建立“源码地图”。

### `config.py`

作用：

- 统一管理项目的路径、端口、主机地址、模型目录、数据集目录、Milvus 和 Neo4j 配置

你可以把它理解成：

```text
整个项目的集中式配置入口
```

### `app.py`

作用：

- 在线检索主入口
- 加载模型
- 获取候选 scene
- 编码文本
- 搜索 Milvus
- 补全命中元数据
- 生成图片结果或视频结果
- 构建 Gradio 页面

你可以把它理解成：

```text
在线检索编排层 + 结果展示层的总入口
```

### `src/kg_builder.py`

作用：

- 从 nuScenes 元数据整理 scene 级 record
- 生成本地 scene 结构化卡片
- 写入 Neo4j 知识图谱
- 从 Neo4j 查询符合条件的 scene token

你可以把它理解成：

```text
场景整理层 + 知识图谱层的核心文件
```

### `src/nlp_parser.py`

作用：

- 把自然语言查询拆成结构化条件
- 判断语言
- 为后续模型路由提供依据

### `src/nuscenes_metadata.py`

作用：

- 把 CSV 里的图片路径重新对齐到 nuScenes 元数据
- 找到某张图片对应的 `scene_token`、`sample_token`、`camera`
- 补出 `weather`、`timeofday`、`location`、`obj_types`

它是整个项目里非常关键但容易被低估的桥接层。

### `src/milvus_utils.py`

作用：

- 定义 Milvus collection schema
- 定义索引参数和搜索参数
- 管理 collection 的创建、加载、字段检查

### `scripts/insert_image.py`

作用：

- 离线构建图片帧向量库
- 将图片 embedding 和元数据插入 Milvus

### `scripts/evaluate.py`

作用：

- 评估 `Pure CLIP` 和 `KG + CLIP` 两种检索策略
- 计算 `Precision@K`、`Recall@K`、`mAP` 和响应时间

### `start.bat`

作用：

- 在 Windows 下检查环境
- 启动 Neo4j、Milvus、Attu
- 启动 Gradio 应用
- 打印访问地址和启动状态

## 4. 七层分层理解

## 第 1 层：原始数据层

这一层就是 `nuScenes` 数据集本体，是整个项目的原材料仓库。

它主要回答的问题是：

- 有哪些 scene
- 每个 scene 里有哪些关键时刻
- 每个关键时刻有哪些相机画面
- 每个关键时刻有哪些对象标注
- 这些标注最终属于哪些语义类别

这一层没有“业务逻辑”，它只提供原始事实。

### 4.1 目录和路径

在当前项目配置里，数据集路径由 `config.py` 指定：

- `NUSCENES_ROOT = D:\nuScenes_v1.0-mini`
- `NUSCENES_VERSION = v1.0-mini`
- `NUSCENES_META_DIR = D:\nuScenes_v1.0-mini\v1.0-mini`
- `NUSCENES_SAMPLES_DIR = D:\nuScenes_v1.0-mini\samples`
- `NUSCENES_SWEEPS_DIR = D:\nuScenes_v1.0-mini\sweeps`
- `PRIMARY_CAMERA = CAM_FRONT`

### 4.2 这一层真正依赖哪些原始文件

项目里真正依赖的原始文件是：

- `scene.json`
- `sample.json`
- `sample_data.json`
- `sample_annotation.json`
- `instance.json`
- `category.json`
- `log.json`
- `samples/`
- `sweeps/`

下面逐个讲这些文件“里面有什么字段”和“在这个项目里怎么被使用”。

### 4.3 `scene.json`

作用：

- 定义“有哪些 scene”
- 给出每个 scene 的名字、描述、首尾 sample 等信息

典型字段：

- `token`
- `log_token`
- `nbr_samples`
- `first_sample_token`
- `last_sample_token`
- `name`
- `description`

当前数据集中第一条示例大致是：

```text
token=cc8c0bf57f984915a77078b10eb33198
log_token=7e25a2c8ea1f41c5b0da1e69ecfa71a2
nbr_samples=39
first_sample_token=ca9a282c9e77460f8360f564131a8af5
last_sample_token=ed5fc18c31904f96a8f0dbb99ff069c0
name=scene-0061
description=Parked truck, construction, intersection, turn left, following a van
```

这些字段在项目中的意义：

- `token`
  - scene 的唯一 ID，是后面一切 scene 级关联的主键
- `log_token`
  - 用来关联 `log.json`，拿到采集区域，比如 `singapore-onenorth`
- `nbr_samples`
  - 当前 scene 的关键时刻数量
- `first_sample_token` 和 `last_sample_token`
  - 表示 scene 的时间边界
- `name`
  - 页面展示和结果解释时常用
- `description`
  - 第 2 层会根据它推断天气、时段、地点类型

项目里哪些函数会读取它：

- `src/kg_builder.py` 中的 `load_metadata_tables`
- `src/kg_builder.py` 中的 `build_scene_records`
- `src/nuscenes_metadata.py` 中的 `load_nuscenes_metadata`
- `app.py` 中的 `load_nuscenes_index`

可以把 `scene.json` 理解成：

```text
scene 级目录表
```

### 4.4 `sample.json`

作用：

- 定义 scene 中每一个关键时刻

典型字段：

- `token`
- `timestamp`
- `prev`
- `next`
- `scene_token`

当前数据集中第一条示例大致是：

```text
token=ca9a282c9e77460f8360f564131a8af5
timestamp=1532402927647951
prev=
next=39586f9d59004284a7114a68825e8eec
scene_token=cc8c0bf57f984915a77078b10eb33198
```

这些字段在项目中的意义：

- `token`
  - sample 的唯一 ID
- `timestamp`
  - 关键时刻的时间戳
- `prev` / `next`
  - 关键时刻之间的前后关系
- `scene_token`
  - 这个 sample 属于哪个 scene

项目里最重要的用法是：

- 构建 `sample -> scene` 映射
- 后续从 `sample_annotation` 回溯到所属 scene 时要用它

项目里读取它的函数包括：

- `src/kg_builder.py` 中的 `build_scene_records`
- `src/nuscenes_metadata.py` 中的 `load_nuscenes_metadata`
- `app.py` 中的 `load_nuscenes_index`

可以把 `sample.json` 理解成：

```text
scene 里的关键时刻目录表
```

### 4.5 `sample_data.json`

作用：

- 定义某个关键时刻下某个具体传感器的数据

注意：

- 这个文件不只包含相机图像
- 也包含雷达、激光雷达等非图像数据

典型字段：

- `token`
- `sample_token`
- `ego_pose_token`
- `calibrated_sensor_token`
- `timestamp`
- `fileformat`
- `is_key_frame`
- `height`
- `width`
- `filename`
- `prev`
- `next`

当前数据集中第一条示例是一个雷达文件，不是图片：

```text
filename=sweeps/RADAR_FRONT/...pcd
fileformat=pcd
is_key_frame=False
```

这恰好说明一个很重要的实现细节：

```text
sample_data.json 是“所有传感器数据”的总表，
而本项目只关心其中的图像行。
```

项目里怎么处理它：

- `src/nuscenes_metadata.py` 中的 `load_nuscenes_metadata`
  - 只保留后缀是 `.jpg`、`.jpeg`、`.png` 的记录
- `app.py` 中的 `load_nuscenes_index`
  - 同样只保留图像记录

从图像行里，项目会提取出：

- `sample_data_token`
- `sample_token`
- `scene_token`
- `timestamp`
- `filename`
- `camera`
- `is_key_frame`
- `prev`
- `next`

其中最重要的字段是：

- `sample_token`
  - 关联到关键时刻
- `filename`
  - 定位到实际图像文件
- `timestamp`
  - 用于视频序列排序
- `is_key_frame`
  - 区分关键帧和连续帧
- `prev` / `next`
  - 表示 sample_data 级别的时序关系

它在项目里的关键用途：

- 通过路径找到某张图对应的 sample_data
- 推断相机通道，比如 `CAM_FRONT`
- 构建 `(scene_token, camera)` 的时间序列
- 为 `text2video` 提供邻近帧收集基础

你可以把 `sample_data.json` 理解成：

```text
每个关键时刻下所有传感器文件的总索引
```

### 4.6 `sample_annotation.json`

作用：

- 定义每个 sample 里的目标标注

典型字段：

- `token`
- `sample_token`
- `instance_token`
- `visibility_token`
- `attribute_tokens`
- `translation`
- `size`
- `rotation`
- `prev`
- `next`
- `num_lidar_pts`
- `num_radar_pts`

当前数据集中第一条示例大致是：

```text
sample_token=cd21dbfc3bd749c7b10a5c42562e0c42
instance_token=6dd2cbf4c24b4caeb625035869bca7b5
visibility_token=4
translation=...
size=...
rotation=...
num_lidar_pts=5
num_radar_pts=0
```

在这个项目里，`sample_annotation.json` 最重要的并不是几何框本身，而是两件事：

- 这条标注属于哪个 `sample`
- 这条标注对应哪个 `instance`

项目怎么使用它：

- `src/kg_builder.py`
  - 遍历所有 annotation，把一个 scene 中出现过的对象实例聚合起来
- `src/nuscenes_metadata.py`
  - 构建 `annotations_by_sample`
  - 后续可据此统计某个 sample 中出现过哪些对象类别

它在本项目中的核心角色可以概括为：

```text
连接“关键时刻”和“对象实例”
```

### 4.7 `instance.json`

作用：

- 定义“对象实例”这一层

典型字段：

- `token`
- `category_token`
- `nbr_annotations`
- `first_annotation_token`
- `last_annotation_token`

当前数据集中第一条示例大致是：

```text
token=6dd2cbf4c24b4caeb625035869bca7b5
category_token=1fa93b757fc74fb197cdd60001ad8abf
nbr_annotations=39
first_annotation_token=...
last_annotation_token=...
```

在项目里的意义：

- `instance_token` 是“同一个物体跨多帧的身份”
- `category_token` 告诉你这个实例属于哪个类别

项目主要使用方式：

- `src/kg_builder.py` 中构建 `instance_to_category`
- `src/nuscenes_metadata.py` 中构建 `instance_to_category`

它的核心作用是：

```text
把“某一个具体对象”映射到“这个对象属于什么类别”
```

### 4.8 `category.json`

作用：

- 定义对象类别

典型字段：

- `token`
- `name`
- `description`

当前数据集中第一条示例大致是：

```text
token=1fa93b757fc74fb197cdd60001ad8abf
name=human.pedestrian.adult
description=Adult subcategory.
```

在项目中的意义：

- `name` 是后续对象语义归一化的来源

项目如何使用它：

- 先通过 `category_token -> name`
- 再通过 `normalize_object_name` 把原始类别名统一成内部对象名

例如：

- `human.pedestrian.adult` -> `pedestrian`
- `vehicle.car` -> `car`
- `vehicle.bus` -> `bus`

你可以把它理解成：

```text
对象语义字典
```

### 4.9 `log.json`

作用：

- 提供数据采集的区域和一些采集背景信息

典型字段：

- `token`
- `logfile`
- `vehicle`
- `date_captured`
- `location`

当前数据集中第一条示例大致是：

```text
token=7e25a2c8ea1f41c5b0da1e69ecfa71a2
logfile=n015-2018-07-24-11-22-45+0800
vehicle=n015
date_captured=2018-07-24
location=singapore-onenorth
```

在项目里的最关键字段是：

- `location`

因为项目会用它作为：

- `location_area`
- `location_key` 的一部分
- 构建 `NEARBY` 场景辅助关系的依据

项目里读取它的函数包括：

- `src/kg_builder.py` 中的 `build_scene_records`
- `src/nuscenes_metadata.py` 中的 `build_scene_metadata`

你可以把它理解成：

```text
scene 的地理背景补充表
```

### 4.10 `samples/` 目录

作用：

- 保存关键帧图像

目录结构通常类似：

```text
samples/
  CAM_FRONT/
  CAM_FRONT_LEFT/
  CAM_FRONT_RIGHT/
  CAM_BACK/
  CAM_BACK_LEFT/
  CAM_BACK_RIGHT/
```

在本项目中的用途：

- 作为图片检索结果展示的真实图像来源
- 作为 `frame_path` 解析的主要目标目录
- 命中帧通常很多来自这里

可以把它理解成：

```text
关键帧图片仓库
```

### 4.11 `sweeps/` 目录

作用：

- 保存连续帧或非关键帧数据

在本项目中的用途：

- 为视频模式提供更连续的时间序列
- 让 `text2video` 能围绕 anchor frame 收集邻近帧

要注意：

- `sweeps/` 里不只有图像，也可能有其他传感器数据
- 本项目处理图像时，只会关注图像文件

你可以把它理解成：

```text
连续帧仓库
```

### 4.12 原始数据层最核心的两条关系链

第一条，场景到图片：

```text
scene.json
  -> sample.json
  -> sample_data.json
  -> samples/ 或 sweeps/ 中的真实图像文件
```

第二条，场景到对象：

```text
sample_annotation.json
  -> instance.json
  -> category.json
```

再加上 `log.json`，就能补全：

```text
scene -> location_area
```

### 4.13 本层的输入、输出和关键消费函数

输入：

- `nuScenes` 原始 JSON 元数据
- `samples/` 图像
- `sweeps/` 图像

输出：

- 还没有真正的业务输出
- 但会被读成索引、映射和原始中间结构

关键消费函数：

- `src/kg_builder.py::load_metadata_tables`
- `src/kg_builder.py::build_scene_records`
- `src/nuscenes_metadata.py::load_nuscenes_metadata`
- `src/nuscenes_metadata.py::get_image_metadata`
- `app.py::load_nuscenes_index`

一句话总结本层：

```text
第 1 层只提供原始事实，不做检索决策。
```

## 第 2 层：场景整理层

这一层负责把零散的原始数据整理成 scene 级结构化卡片。

核心文件：

- `src/kg_builder.py`

### 5.1 这一层要解决什么问题

原始数据是按 `sample`、`sample_data`、`annotation` 分散存的，但业务上我们希望回答：

- 一个 scene 是白天还是夜晚
- 一个 scene 是晴天还是雨天
- 一个 scene 是路口、斑马线还是停车场
- 一个 scene 里出现过哪些对象类别

所以这一层的目标是：

```text
把逐帧、逐标注的事实
整理成按 scene 描述的结构化摘要
```

### 5.2 这一层的输入

输入来自第 1 层：

- `scene.json`
- `log.json`
- `sample.json`
- `sample_annotation.json`
- `instance.json`
- `category.json`

### 5.3 这一层的核心函数

#### `read_json_records`

作用：

- 读取一个 JSON 文件

#### `normalize_object_name`

作用：

- 将 nuScenes 原始类别归一化为项目内部对象名

例如：

- `human.pedestrian.adult` -> `pedestrian`
- `vehicle.car` -> `car`
- `vehicle.bus` -> `bus`

#### `infer_weather`

作用：

- 从 scene 的描述文本中推断天气

当前规则比较简单，主要归类为：

- `rainy`
- `foggy`
- `clear`

#### `infer_time_of_day`

作用：

- 从 scene 描述中推断时段

当前归类为：

- `night`
- `dusk`
- `day`

#### `infer_location_kind`

作用：

- 从 scene 描述中推断地点类型

当前常见类型包括：

- `intersection`
- `crosswalk`
- `parking_lot`
- `bus_stop`
- `sidewalk`
- `highway`
- `street`
- 默认 `urban`

#### `load_metadata_tables`

作用：

- 一次性加载这一层所需的元数据表

#### `build_scene_records`

作用：

- 构建 scene 级 record，是这一层最核心的函数

它做的几件关键事：

1. 加载所有必要元数据表
2. 构建 `sample -> scene` 映射
3. 构建 `instance -> category` 映射
4. 遍历所有 annotation，把对象实例归并到所属 scene
5. 从 `scene.description` 推断天气、时段、地点类型
6. 生成每个 scene 的结构化 record

最终 record 大致长这样：

```python
{
    "scene_token": "...",
    "scene_name": "...",
    "description": "...",
    "num_samples": 39,
    "weather": "clear",
    "timeofday": "day",
    "location_area": "singapore-onenorth",
    "location_kind": "intersection",
    "location_key": "singapore-onenorth|intersection",
    "objects": {
        "traffic_cone": 71,
        "barrier": 65,
        "pedestrian": 60,
        "car": 14
    }
}
```

#### `filter_scene_records`

作用：

- 对 `build_scene_records()` 的输出做本地过滤
- 不依赖 Neo4j

它会逐条判断：

- `weather` 是否匹配
- `timeofday` 是否匹配
- `location_kind` 是否匹配
- 所有 `object_types` 是否都出现在该 scene 中

返回值是：

- 满足条件的 `scene_token` 列表

因此可以把它理解成：

```text
纯 Python 版 scene 级条件过滤器
```

#### `print_summary`

作用：

- 打印 scene records 摘要，方便人工检查

#### `main`

作用：

- 本文件的命令行入口

它的工作模式包括：

- 只构建并打印 scene 摘要
- 只做本地过滤
- 写入 Neo4j
- 写入 Neo4j 后再查询

### 5.4 这一层的输出

输出是：

- `list[dict]` 形式的 scene records

这就是后面知识图谱层的直接输入。

一句话总结本层：

```text
第 2 层把原始数据加工成“scene 结构化卡片”。
```

## 第 3 层：知识图谱层

这一层负责把 scene 卡片变成 Neo4j 图结构。

核心文件：

- `src/kg_builder.py`

### 6.1 图中有哪些节点

当前主要有 5 类节点：

- `Scene`
- `Weather`
- `TimeOfDay`
- `Location`
- `Object`

### 6.2 图中有哪些关系

当前主要有这些关系：

- `Scene -[:WEATHER]-> Weather`
- `Scene -[:TIMEOFDAY]-> TimeOfDay`
- `Scene -[:LOCTYPE]-> Location`
- `Scene -[:CONTAINS]-> Object`
- `Scene -[:NEARBY]-> Scene`

通俗解释：

- `WEATHER`
  - 这个 scene 属于什么天气
- `TIMEOFDAY`
  - 这个 scene 属于什么时段
- `LOCTYPE`
  - 这个 scene 属于什么地点类型和区域组合
- `CONTAINS`
  - 这个 scene 里出现过哪些对象类别
- `NEARBY`
  - 两个 scene 处于相同 location_area，因此建立辅助连接

### 6.3 `MERGE` 是什么意思

Neo4j 里的 `MERGE` 可以理解成：

```text
有就复用，没有就创建
```

例如：

```cypher
MERGE (s:Scene {scene_token: $scene_token})
```

表示：

- 如果这个 `scene_token` 的场景节点已经存在，就使用现有节点
- 如果不存在，就创建一个新的

### 6.4 `[:WEATHER]` 是什么意思

这是关系类型语法。

例如：

```cypher
(s)-[:WEATHER]->(w)
```

通俗翻译成中文就是：

```text
从节点 s 出发，有一条类型叫 WEATHER 的边，指向节点 w
```

代入具体例子：

```text
(scene-0061)-[:WEATHER]->(clear)
```

等价于：

```text
scene-0061 的天气是 clear
```

### 6.5 图关系和过滤为什么是连在一起的

这是图数据库最容易让人迷糊的地方。

在传统关系表里，你可能写：

```text
scene.weather = rainy
scene.time = night
```

但在图数据库里，过滤的逻辑不是“按列判断”，而是：

```text
看某个 Scene 节点是否沿着指定关系，
连到了用户要求的那些节点。
```

例如用户查询：

```text
雨天夜晚路口有行人
```

系统会先把它解析成：

- `weather = rainy`
- `timeofday = night`
- `location_kind = intersection`
- `object_types = ["pedestrian"]`

然后 Neo4j 会检查每个 `Scene`：

1. 是否存在 `Scene -[:WEATHER]-> Weather(name="rainy")`
2. 是否存在 `Scene -[:TIMEOFDAY]-> TimeOfDay(name="night")`
3. 是否存在 `Scene -[:LOCTYPE]-> Location(kind="intersection")`
4. 是否存在 `Scene -[:CONTAINS]-> Object(name="pedestrian")`

如果 4 个条件都满足，这个 scene 才会被留下。

要特别区分两层含义：

- 单个 scene 只要有一个条件不满足，就被过滤掉
- 不是“某一个 scene 失败就立刻全库检索”
- 系统会继续检查其他 scene
- 只有当所有 scene 都没留下时，候选 scene 列表才会为空

### 6.6 Neo4j 在这个项目里的检索原理

Neo4j 不是做向量相似度排名的。

它做的是：

```text
scene 级条件过滤
```

核心函数是：

- `query_scene_tokens`

它会：

1. 从所有 `Scene` 节点开始
2. 逐项检查天气、时段、地点、对象条件
3. 返回满足条件的 `scene_token`

所以 Neo4j 在这个项目里的角色是：

```text
先缩小搜索范围，不负责最终相似度排序
```

一句话总结本层：

```text
第 3 层用图关系表达 scene 的条件约束，并据此筛选候选 scene。
```

## 第 4 层：自然语言理解层

这一层负责把用户的人话变成系统可用的结构化条件。

核心文件：

- `src/nlp_parser.py`

### 7.1 这一层解决什么问题

例如用户输入：

```text
雨天夜晚十字路口有行人
```

系统需要把它拆成：

- `weather = rainy`
- `time = night`
- `location = intersection`
- `objects = ["pedestrian"]`

同时还要判断：

- 这句话是中文还是英文
- 后面应该默认走哪个 CLIP 模型

### 7.2 这一层的主要函数

#### `detect_language`

作用：

- 判断文本里是否包含中文字符

#### `select_model_key`

作用：

- 根据语言选择 `chnclip` 或 `engclip`

#### `_contains_keyword`

作用：

- 判断查询文本中是否包含某个关键词

#### `_match_first`

作用：

- 在一组关键词映射里找到第一个命中的标签

用于：

- 天气
- 时段
- 地点

#### `_match_all`

作用：

- 找到所有命中的标签

主要用于：

- 对象类别提取

#### `parse_query`

作用：

- 综合调用上述逻辑，输出结构化查询结果

输出结果包含：

- `weather`
- `time`
- `objects`
- `location`
- `language`
- `model_key`
- `raw_text`

### 7.3 这一层的特点

- 当前是规则解析，不是大模型解析
- `weather/time/location` 多为单值
- `objects` 可以是多值
- 一头连接知识图谱，一头连接文本编码模型

一句话总结本层：

```text
第 4 层把用户的人话翻译成“可过滤 + 可路由”的结构化查询。
```

## 第 5 层：向量检索层

这一层负责回答：

```text
用户这句话在视觉语义上最像哪些帧
```

相关文件：

- `src/milvus_utils.py`
- `src/nuscenes_metadata.py`
- `scripts/insert_image.py`
- `app.py`

### 8.1 这一层分两部分

第一部分：

- 离线建帧向量库

第二部分：

- 在线把文本编码成向量，再去向量库中搜索

### 8.2 Milvus 中到底存什么

`src/milvus_utils.py` 中定义了 schema。

当前每条记录的核心字段是：

- `id`
- `embedding`
- `scene_token`
- `sample_token`
- `camera`
- `frame_path`
- `weather`
- `timeofday`
- `location`
- `obj_types`

因此 Milvus 中的一条数据不是：

```text
一个 scene
```

也不是：

```text
一个视频
```

而是：

```text
一张帧图片及其 embedding 和元数据
```

### 8.3 什么叫“补全元数据”

通俗讲，就是把原本只有 `id + path` 的图片行，补成“这张图在业务上是谁”。

具体来说，`scripts/insert_image.py` 在入库前会通过 `src/nuscenes_metadata.py::get_image_metadata` 补出：

- `scene_token`
- `sample_token`
- `camera`
- `frame_path`
- `weather`
- `timeofday`
- `location`
- `obj_types`

这样一张图在 Milvus 里就不只是“向量”，还带着：

- 它属于哪个 scene
- 它来自哪个关键时刻
- 它属于哪个相机
- 它所在 scene 是什么天气、时段、地点
- 它所在 sample 里出现过什么对象

这一步非常重要，因为后面的：

- scene 过滤
- 结果解释
- 视频拼接
- 卡片展示

都依赖这些元数据。

### 8.4 旧版 `insert_image.py` 和新版对比

用户曾提供上一项目中的 `D:\NLP_Retrieval_System\insert_image.py`。

两者相似点：

- 都是读 CSV
- 都是图片编码
- 都是向量归一化
- 都是插入 Milvus

旧版特点：

- 更像快速 demo
- Towhee pipeline 串联
- 基本只插入 `id + vec`
- 配置硬编码更多
- 几乎没有业务元数据

新版特点：

- 使用 `config.py`
- 使用 `nuscenes_metadata` 对齐数据集元信息
- 插入 embedding 之外还插入业务元数据
- 支持 schema 检查、批量插入、限量插入、重建 collection

结论：

```text
如果是当前项目，新版更合适。
```

因为现在项目不只是向量 demo，而是一个带知识图谱、解释和视频派生能力的完整检索系统。

### 8.5 在线检索时怎么工作

在线查询时，系统会：

1. 根据语言选择文本编码模型
2. 把查询文本编码成向量
3. 去 Milvus 中检索最相似的帧向量
4. 返回帧级命中结果

### 8.6 CLIP 的工作原理

CLIP 的核心思想是：

```text
把文字和图片放进同一个可比较的语义空间
```

它由两条编码器分支构成：

- 文本编码器
- 图像编码器

训练时，它会学习：

- 匹配的图文对要靠近
- 不匹配的图文对要远离

所以检索时，本质上是在做：

```text
找哪些图片向量最接近这句话的文本向量
```

最通俗的理解是：

```text
CLIP 不是在背固定标签，
而是在学习图和文的共同语义坐标系。
```

一句话总结本层：

```text
第 5 层把文本和图片帧映射到同一向量空间，并用 Milvus 找出最相似的帧。
```

## 第 6 层：检索编排层

这一层是在线系统的总调度中心。

核心文件：

- `app.py`

### 9.1 这一层负责什么


### 9.3 关键函数

#### `dynamic_retrieve`

#### `retrieve_images`

作用：

- 处理 `text2image`

流程：

1. 解析查询
2. 获取候选 scene
3. 编码文本
4. 搜索 Milvus

#### `retrieve_videos`

## 6. 常见易混点

### 6.1 Neo4j 和 Milvus 谁负责什么

- Neo4j：负责 scene 级条件过滤
- Milvus：负责帧级语义相似度检索

### 6.2 为什么一个 scene 不满足条件，不会立刻全库检索

因为：

- 单个 scene 不满足，只是淘汰这个 scene
- 系统会继续看其他 scene
- 只有所有 scene 都没留下来，候选列表为空时，才会回退到全库搜索

### 6.3 为什么一再强调 Milvus 存的是帧

因为这决定了系统真实的检索粒度：

- 真正被检索的是图像帧
- 视频只是围绕命中帧动态生成

### 6.4 为什么 `sample_data.json` 这么重要

因为它把：

- 路径
- 相机
- 时间顺序
- sample 归属

这些视频生成和图像对齐最关键的信息都串起来了。

### 6.5 为什么新版 `insert_image.py` 比旧版更适合当前项目

因为当前项目已经不是简单向量 demo，而是要求：

- scene 可过滤
- 结果可解释
- 命中帧可追溯
- 视频可派生

这些都要求 Milvus 里不只是有 embedding，还要有足够完整的元数据。

## 8. 一页总结整个项目

这个项目不是一个简单的文搜图脚本，而是一个由数据整理、知识图谱、向量检索、检索编排和结果展示共同组成的自动驾驶场景检索系统。系统先从 `nuScenes` 的原始 JSON 元数据和图像目录中提取 scene、sample、sample_data、annotation、instance、category 和 log 等信息，然后将它们整理成 scene 级结构化记录，并进一步写入 Neo4j 形成知识图谱。在在线查询时，系统先将用户自然语言解析为天气、时段、地点和对象等条件，用 Neo4j 或本地 scene records 进行 scene 级过滤，再使用 CLIP 将查询文本编码成向量，在 Milvus 中对帧级 embedding 进行相似度检索。最终，`text2image` 直接返回命中的图片帧，而 `text2video` 则围绕命中帧动态收集邻近帧并生成视频片段。整个流程由 `app.py` 统一编排，并通过 Gradio 页面展示出来。
